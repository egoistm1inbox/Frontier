# Native Lens Flare inspector — first implementation

This follows the inspection in [LensFlareNativeAudit.md](LensFlareNativeAudit.md). It adds a real native InspectorPanel route, a shared procedural image, editable custom layers, and matching viewport-shader inputs. It is **not** a finished scene baked-image playback system or a certified browser-pixel-identical port.

## Panel and controls

The composition follows `flare-inspector.jsx`: a large composite image above the layer and ghost cards, existing C++ SliderPill controls, a horizontal row of three Sun-style quick tiles (green ON / red OFF, no tick boxes), shape choices and ghost count controls. A top baking card follows the user's requested placement. Additional halo and legacy-preset controls preserve useful native parameters.

- **Anamorphic:** horizontal blue optical streak; remains horizontal when Rotation changes.
- **Streaks:** independently switchable warm, rotatable streak.
- **Starburst:** independently switchable radial effect; integer Ray pairs controls 2N primary rays.
- **Ghosts:** 0–24 elements in Custom layers mode; round, hexagonal or octagonal profiles, brightness and optical-axis spacing.
- **Halo:** radius, width and brightness, independent of the three primary effect switches.
- **Common controls:** intensity, spread, chromatic blend and streak gain.
- **Preview source:** draggable, keyboard-arrow positioning (Shift for larger steps), and Recenter. This authoring pose never overwrites the actual Sun or camera.
- **Legacy presets:** Cinematic, Anamorphic, Starburst and Halo remain selectable. Existing appearance remains the default; Custom layers is an explicit fifth selection or activates when a custom layer control is edited. Legacy presets retain round ghosts capped at eight and their original blade-based burst. The UI states those limits. Aperture Blades remains a legacy control; Custom uses Ray pairs instead.

All 21 sheet fields have backend bindings. The new route uses `EditorSheetAppearance::LensFlare`; other entities still reset to Generic. `BuildFlareSheet` is separate from the large non-Sun dispatcher to keep its stack use measurable.

## One image, not two separate drawings

The panel owns a **640×280 linear RGB cache** and one context-managed ImGui RGBA texture. The top thumbnail and large composite reference the **same texture**, with correct aspect ratio. The image is generated by `AtmosphericOptics::LensFlare`, which dispatches Custom layers to the shared kernel. It is not the HTML canvas renderer or an SVG approximation.

Cache keys include every relevant property and authoring source position. Unchanged frames reuse the image; parameter/pose changes regenerate it. The linear data and display pixels use about **2.73 MiB on the heap**, not large stack arrays. Rendering cost on regeneration has not been performance-certified. This version has one flare-authoring resource per ImGui context, matching the single Lens Flare entity; multiple independently edited flare inspectors within one context are not supported yet.

The display uses `linear / (1 + linear)` followed by the sRGB transfer. That is an authoring preview transform, not a claim of matching every viewport exposure setting.

### Bake / export

**Bake / export HDR** writes the cached linear RGB pixels to `Exports/LensFlare.pfm`, relative to the native application's working directory. PFM rows are written bottom-up with an explicit host-endian scale sign. This is additive HDR light, not a transparent PNG with invented alpha. Export success records the cache revision; subsequent changes visibly mark the exported bake out of date.

**Use baked image is disabled.** No image import, persisted baked asset reference or camera-dependent scene playback is claimed. A full-frame flare image depends on source position/aspect; wiring scene playback requires either matching those inputs or a component-atlas approach. The tab's current preview is live procedural output, not a frozen imported image.

## Algorithm and renderer binding

`Engine/DisplayPresentation/LensFlareKernel.h` is a scalar shared C++ / GLSL-style Slang source, used by:

1. C++ `AtmosphericOptics::LensFlare` for Custom layers, including the authoring image.
2. `Engine/Shaders/PostRecords.slang::FlareAlong` for Custom layers in the viewport ray-tracing shader.

It supports independent cool/warm/radial layers, integer-periodic radial rays, polygonal ghost distance profiles, ghost spacing/gain and independently adjustable halo width/gain. Zero-radius angular evaluations have explicit guards. It is an artist-controllable optical-effect approximation, not physical lens-element ray tracing.

`CelestialSequence::ApplySheet` validates finite scalar input, clamps ranges and rounds counts. Custom control changes activate Custom mode; an explicitly changed preset selection takes precedence if supplied simultaneously. `PackPostRecord` sends these settings to the viewport. Existing Sun visibility, scene enable and occlusion gates remain in the renderer; preview visibility is deliberately an authoring fixture.

### Uniform ABI change — apply as a unit

The post record grows from **128 to 192 bytes**. The first eight rows preserve their offsets. Four appended rows at **128, 144, 160 and 176** carry 16 custom parameters. `PostFlareUv.w` selects the custom kernel. The C++ struct, packer, shader block and DeviceExchange buffer/copy size are all patched together. **Rebuild shaders and host together; do not combine an old 128-byte host with the new shader.**

Actual SPIR-V reflection confirms the 192-byte block at binding 24 and all four appended offsets (`ShaderLayout.txt`).

### Deliberately unfinished paths

- The separate `RendererHost::ApplyLensFlare` CPU showcase/export path still uses its legacy `FlareSpecification.slang` configuration. This change does not claim to connect that exporter to every native slider. Consolidating it remains a follow-up.
- Legacy presets keep the old artistic burst implementation; the audit's odd-blade concern is not silently declared fixed. The new Custom ray-pair kernel is periodic and tested independently.
- Scene use of baked images, import and persistence remain pending.
- Full application/device execution, GPU numeric parity and Windows/MSVC stack measurements remain unverified.
- Native ImGui managed-texture support is required. The normal renderer backend must shut down **before** destroying the ImGui context; the context hook then releases the CPU cache and unregisters the image. CPU proof teardown and leak detection pass, but GPU resource teardown has not been exercised on hardware.

## Executed proof

`Exhibits/Workbench/LensFlare/RunNativePanel.py` reconstructs the pinned target with the ordered integration patches, runs the Sun regression, then builds/runs the real native Lens Flare inspector and sequence.

- **74 Lens Flare checks pass** in release, debug, and ASan/UBSan with leak detection.
- **326 Sun regression checks pass** in all three modes.
- Real pointer changes to native sliders, layer buttons, ghost count and shape, and source dragging; keyboard source positioning.
- Actual CPU pixel changes for every custom scalar/component; parameter bounds/nonfinite inputs; preset/custom transitions.
- Shared texture identity across thumbnail and composite, unchanged-frame caching, edit invalidation, export revision tracking and stale-bake detection.
- Exported HDR samples equal actual algorithm output; renderer-record flags/parameters and ABI size are checked.
- Narrow scrolling, compact 320px control fit, 2× framebuffer capture, sheet reuse and context teardown.
- New panel compiles with `-Wall -Wextra -Werror`.
- **18/18 engine shaders compile to SPIR-V** using glslang **16.6.0**, built from the tagged upstream source. Viewport uniform-block reflection passes. Compilation is not GPU execution or image parity.
- Both editor host source files pass the existing syntax check; target CMake integration applies. No complete device build is claimed.

Five losslessly compressed captures are in `Exhibits/Gallery/LensFlareNative/`. The server on **5179** is a read-only capture viewer, not an interactive HTML copy of the native controls. The approved Sun viewer remains on 5177.

### Stack measurements

Release and debug proofs run with a **256 KiB Linux stack limit**. Individual compiler-reported frames:

| Function | Release | Debug |
|---|---:|---:|
| BuildFlareSheet | 320 B | 5,776 B |
| RecordLensFlareInspector | 720 B | 1,152 B |
| Preview update | 544 B | 608 B |
| ApplySheet | 208 B | 304 B |
| Lens proof main | 1,920 B | 2,608 B |

Measured entry points are gated at 8 KiB per function. These are not summed runtime high-water marks, and they do not certify Windows stack reserve/commit or the entire application call chain.

## Reproduction and integration

```sh
python3 Exhibits/Workbench/LensFlare/RunNativePanel.py
python3 Exhibits/Workbench/LensFlare/RunNativePanel.py --debug
python3 Exhibits/Workbench/LensFlare/RunNativePanel.py --sanitize
python3 Exhibits/Workbench/LensFlare/ServeNativePanel.py --port 5179
```

Requires the prepared pinned target and exact dependencies used by the Sun proof. The runner handles reconstruction and regresses Sun first. `--reuse-build` is only for an already matching build mode/source state.

Apply `LensFlareInspector.patch` **after** NativeOutliner, SunInspector, FullSunInspector, SunLightingBindings and SunMotionBindings. Copy `LensFlareKernel.h` into Engine/DisplayPresentation and `LensFlareInspectorPanel.h/.cpp` plus its NOTICE into Engine/Editor. Preserve the existing Sun files/fonts and preceding integration. CMake adds the Lens Flare source and registers the shared kernel header as a shader rebuild dependency. Rebuild both host and shaders for the new record size.

Shader check after staging, with a working glslang on PATH:

```sh
cd .cache/cpp-sun-full
bash Tools/Build/CheckShaders.sh
```

The original immutable target was not modified. Source/capture hashes, commands, proof results and stack evidence accompany the gallery.
