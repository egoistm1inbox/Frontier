Building a standalone matcap viewport validation panel. Workspace name is **SketchModelViewport** (user directed: use the Sketching register, do NOT use the words "Draft"/"Drafting"; `Cad`/`CAD` also barred by [[SKILL-Naming]]). Distinct from the existing `ParametricSketcher` editor/workspace, which is 2D constraint sketching — this is the 3D matcap solid-model viewport. Source of truth for the UI is `Documentation/Prototypes/CadModellingInterface.html`.

User decisions (2026-07-28):
- **Matcap renders REAL B-rep geometry** — shells / extrusions / solids / lofts (geometry arrives later, but the plan/architecture must support it from the start, not a demo-mesh hack).
- **Scaffold = SketchOutliner / Vulkan spine** (`PlatformWindow` + `VulkanHost` + `VulkanImguiInterface` + `SvgIconRegistry`; links EngineContext+Graphics+Platform).
- **Multiple standalone exes** — isolate each component (viewport exe + component-exercise exes).

Rendering decision: **extend the existing visibility path**, do NOT build a separate matcap pipeline and do NOT use the software rasterizer as-is. Visibility buffer is `R32_UINT` identity + D32 depth, identity = `(partition<<20)|(triangle&0xFFFFF)` = full surface handle. Matcap needs a per-pixel normal which the resolve does NOT currently carry → new `MatcapInscription` shading unit samples resolved id+depth, re-derives the triangle from the identity, interpolates uploaded vertex normals (RenderVertex stride-32 already has normal). Naming: `…Inscription` = composites onto an existing target (per [[SKILL-Naming]] render-unit suffixes).

**GRID IS GPU (user directed 2026-07-28).** The dotted grid must run on the GPU, NOT the ImDrawList placeholder in `ViewportPanel.cpp`. The shader already exists: `Internal/Graphics/Grid/GroundGridPass.{h,cpp}` + `Shaders/AnalyticGroundPlane.{vert,frag}` — a Blender-style analytic grid reconstructed from the camera's InverseViewProjection (one fullscreen triangle, no vertex buffers). It has a dedicated **dotted layer** (`DotLayerEnabled`, `DotColour`, dots on major-line intersections) plus line + axis layers, each toggleable — these map 1:1 onto the mockup Settings menu (Grid lines / Dots / None). `RenderExtension` owns a `GridPass` but renders to its OWN swapchain (full renderer app, not offscreen-to-ImGui). NO existing standalone renders GroundGridPass into an ImGui texture — that offscreen (VkImage + view + `ImGui_ImplVulkan_AddTexture`) → `RenderedTexture` plumbing is the real Phase-1 work.

**Phase-1 correction:** the first SketchModelViewport build (Host/Panel/.cpp/.h + Build.bat, all compiling + launching) only re-hosts `ConstructViewportPanel` — the ImDrawList 2D placeholder grid, none of the mockup chrome. That is a boot harness, NOT the viewport. Real Phase 1 = the offscreen GPU-grid plumbing above. The mockup's `.viewport` column = `vp-topbar` (52px) + `canvas-stage` (GPU grid + gizmo-hotspot) + `vp-footer` (30px). The three dropdown pills (Views / Settings / Units) ARE the "buttons/dropdowns" and belong to the viewport chrome (Phase 2), all three fully wired per user.

**Why:** the HTML mockup viewport renders NO 3D geometry (2D grid + gizmo only) — the matcap renderer is net-new beyond a 1:1 chrome copy.

Matcap specifics (2026-07-28): per-pixel normal = **re-derive from identity** (re-fetch triangle via id buffer, interpolate uploaded vertex normals — no raster change, smooth on curved surfaces). Initial matcap = **single neutral studio matcap** bundled with the app (loadable set deferred).

**Phase-1 build seam facts (verified 2026-07-28):**
- `ViewportPanelState.RenderedTexture` was `unsigned` (truncates a 64-bit `VkDescriptorSet` ImTextureID) → WIDENED to `ImTextureID` in the shared `ViewportPanel.h`; the `intptr_t` bounce in `.cpp` removed. `=0`/`!=0` still valid.
- `VulkanImguiInterface` does NOT expose its per-frame command buffer (Begin/Submit own it internally). So the offscreen grid needs its OWN command pool + one-shot command buffer submitted+fence-waited BEFORE `ImGui::Render()` each frame (a stall, fine for a validation tool). Host owns the pool.
- Grid math helpers: `SolveOrbitOrientation` (CameraViewMatrixSolver.h), `EvaluateProjectionFrame` (ProjectionEvaluator.h), `MultiplyMatrix`/`InvertMatrix` (LinearAlgebra_Float32.h inline). Replicated as `AssembleSketchModelGridConstants` in the app panel.
- `.spv` live at `Internal\Graphics\Grid\Shaders\AnalyticGroundPlane.{vert,frag}.spv`; Build.bat copies them to `%OUTDIR%\Shaders`; runtime resolves relative `"Shaders"`.
- ~~Camera bridge~~ **REMOVED 2026-07-29 — see "Camera unified" below.** There is exactly ONE camera now: `Frontier::ViewportCamera` (metres). `PanelViewportCamera` and the bridge are deleted.

**Camera unified (2026-07-29) — the cube/grid desync fix.** ROOT CAUSE was a pitch-sign convention clash across the bridge: `PanelViewportCamera` read `+Pitch = eye above looking down`, but `Frontier::ViewportCamera`'s `ResolveOrbitRotation` NEGATES pitch (`-Pitch = eye above looking down`). The bridge copied pitch verbatim, so the GPU grid tilted opposite to the compass cube (which read the panel cam directly). Fixed by DELETING the dual-camera setup, not by patching signs.
- `Internal/EngineContext/Interface/WorkspaceHost/Viewport/ViewportCamera.{h,cpp}` (the `PanelViewportCamera` definition) are **deleted**. `EngineContext/Build.bat` globs `.cpp` recursively, so no build-list edit was needed.
- `ViewportPanelState.Camera`, `ConstructViewportGrid(..., const ViewportCamera&, ...)`, and `SpatialCompassContext.Camera` are all now `Frontier::ViewportCamera` (metres, negated-pitch).
- Navigation now goes through the shared verbs in `Navigation/Camera/CameraNavigation/`: `OrbitViewportCamera(Cam, YawΔ, PitchΔ)` [rad], `PanViewportCamera(Cam, RightΔ, UpΔ)` [world], `DollyViewportCamera(Cam, DistanceΔ)` [world]. They take ANGLE/WORLD deltas, not pixels, and each reapplies its own constraint internally — so pixel scaling lives in the panel: `OrbitRadiansPerPixel 0.008`, `PanFractionPerPixel 0.0015` (×Distance so the drag tracks the cursor), `DollyFractionPerNotch 0.10` (×Distance).
- 💡 The SpatialCompass needed NO sign flips: `ResolveDisplayAngles` (`Elevation=-Pitch`, `Azimuth=-Yaw`) and `ResolvePresetCameraPose` in `SphericalCoordinateTable.h` were ALREADY authored against `ViewportCamera`'s negated-pitch convention — they were merely *typed* against `PanelViewportCamera`. Only the type swap + `Orthographic bool → ProjectionMode` enum were required.

Unrelated to the camera work: the untracked WIP `SpatialAcceleration/ToroidalClipmapField.cpp` includes `"SpatialAcceleration/ToroidalClipmapField.h"` (EngineContext-rooted, matching what its own `ClipmapFieldValidation/Build.bat` assumes), which the single `/I Internal` root could not resolve — it broke the whole shared pillar.
