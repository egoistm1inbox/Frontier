RenderScope Architecture

Coexisting renderers — PBR, CAD solid, overlay, selection — each a separate static lib a build target either links or does not. Why this beats what Frontier has today, and where it agrees and disagrees with Blender and Unreal Engine 5.

The one-line thesis

The current mess is a build-graph defect, not a code-style defect. One globbed Graphics.lib with /DFRONTIER_POLYGON_AUTHORING hardcoded at Build.bat:63 means every target — including a future game — compiles the authoring renderer in. No amount of #ifdef fixes that. Strip at the lib boundary, order scopes in a fixed list, and keep #ifdef at four declaration sites.

🟢 Verified before designing: all 71 files in Internal/Graphics were include-scanned. The Radiance group includes nothing from Solid/Overlay/Select, and those three have zero edges between them. Your subsystems were already written to this layering — this plan makes the build system honour a separation the code already respects.

01The defect, drawn

Today one lib is produced by globbing every .cpp under Internal/Graphics, and the authoring define is baked into that lib rather than into the targets that want it. A game linking this lib receives CAD, gizmo and selection code it can never use.

03Three independent axes — why "all editors at once" stays fast

The performance question you raised — run every editor in one application and still be fast — resolves into keeping three things separate that are usually conflated. A scope that is compiled in but not active costs one null pointer.

04Frame anatomy — colour scopes and ordering

One shading scope wins the scene target; overlays composite after the tone map so authored colours survive; selection reuses the id buffer the raster already wrote, so it costs no extra geometry pass.

05Compared: current · Blender · Unreal · RenderScope

Frontier today

one lib · one lambda
  • Separation: none — 71 files → 1 lib
  • Ordering: a ~400-line recorder lambda
  • Stripping: impossible; define baked into the lib
  • Spine: RenderSchedule exists but is OFF, 2 of ~12 steps

Blender

draw manager · 10 engines
  • Separation: engines as named slots in DRWViewData
  • Ordering: hand-written foreach_engine list — no solver
  • Stripping: only the debug engine; no runtime build exists
  • Lazy: DrawEngine::Pointer — null until used

Unreal Engine 5

modules · RDG
  • Separation: module "Type" in the descriptor
  • Ordering: RDG — full dependency graph
  • Stripping: UBT prunes before the compiler runs
  • Caveat: WITH_EDITOR alone strips nothing from the build graph

RenderScope

5 libs · fixed list
  • Separation: 5 libs, verified dependency-clean
  • Ordering: fixed list — Blender's model
  • Stripping: lib boundary — Unreal's model
  • Guards: 4 declaration sites, never in a function body

What makes it superior is not novelty — it is picking the right half of each. Blender has excellent scope separation but cannot strip anything, because it has no runtime build to strip for. Unreal can strip beautifully but pays for a full dependency-solving render graph Frontier has no use for at four scopes. RenderScope takes Blender's ordering and Unreal's stripping, and skips both of their costs.

06Why no render graph

The obvious objection: Unreal has RDG, Frostbite has FrameGraph — why a plain ordered list? Because the justification for a solver is a function of scale, and the numbers are not close.

Worth revisiting later, independently: Frostbite's transient resource aliasing — the one render-graph benefit obtainable without a graph, reported to reclaim >50% of resource allocation space.

07The four guard sites

Your concern about #ifdef making the code messy is the right concern — and the fix is positional. Guards go where things are declared, never where work is done. A stripped scope's implementation is not guarded at all; it simply is not compiled.

09Phases and the one real risk

Phase 1
Split into 5 Build.bat; de-hardcode the define at Build.bat:63 — gate: each lib compiles and links alone
Phase 2
Lift ~30 key toggles out of the recorder into ScopeEngagementTable — gate: pixel-identical output
Phase 3
Register every scope as a RenderSchedule step; flip EnabledCondition ON — gate: A/B against the legacy path
Phase 4
Delete the ~400-line legacy recorder
Phase 5
GameProfileValidation target: Substrate + Radiance only — must run in Automation/ValidationRun.ps1

🔴 Phase 5 is load-bearing, not an afterthought. Godot's disable_3d build has been broken more or less continuously from 2015 to 2025 — 114 unresolved externals in the original report, still failing in 4.5. Every single failure was a reverse dependency from debugger, serialization or script-binding glue reaching into the subsystem that was removed. Never the renderer itself.

The lesson transfers exactly: a compile-time toggle that CI does not build will rot. The stripped configuration has to be a build target from day one, which is why phase 5 exists rather than waiting for a real game executable.

Phases 1–2 are mechanical moves behind a pixel-identity check. Phase 3 is where it becomes the new architecture — and the A/B gate it needs is already built into RenderSchedule.
